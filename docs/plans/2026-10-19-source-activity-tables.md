# Source Activity Tables Implementation Plan

**Goal:** Persist editable original-paper Tables plus derived Other, support AI prefill/revision, and run two authorized GPT-6-Astra/high revision examples with reviewer re-confirmation and AI-excluded approval differences.
**Architecture:** Workspace-owned ActivityTable rows store source metadata and column definitions referring to existing Activity IDs, never duplicated values. Existing workspace version locking, history, review status, snapshots and AI provenance apply. Other derives from Activity IDs unassigned to any saved table. AI payload adds optional stable activity refs and table definitions; absent optional collections preserve old serializations/hashes. Scientific runtimes read sources; supervisor reads only outputs/identity metadata.
**Tech Stack:** FastAPI/SQLAlchemy/PostgreSQL/Alembic, Vue3/TypeScript, existing frozen Codex scientific adapter.

## Approved design and wire contract

- Table fields: id(UUID), name, kind(source|custom), source_label, source_title, page_number, review_hint, review_status(draft|reviewer_confirmed|unresolved), columns, mode(any|all), sort(label|similarity|default). Columns: id(string), label, assay, metric, unit(nullable), activity_ids(UUID[]). Source label/title/page optional for custom; source table requires source_label. No automatic source identity inferred from labels.
- GET /api/v2/workspaces/{id}/activity-tables -> workspace_id, workspace_version, tables, other_activity_ids. PUT /api/v2/workspaces/{id}/activity-tables/{table_id} accepts expected_workspace_version plus table writable fields, creates or updates. DELETE version-guarded; POST /.../{table_id}/confirm supports explicit reviewer confirmation. Mutations return workspace_version and table when applicable. Read admin/reviewer authorization and frozen workspace guards reuse current patterns. Backend may refine details in collaboration before frontend integration.
- Tables belong to workspace, not browser/user. Other is computed and not deletable; unmatched means not yet assigned, not necessarily source-outside-table. Current browser tables may explicitly import as custom tables with exact resolved Activity IDs; never relabel inferred tables as original source tables. No silent discard of local saved work.
- Frontend preserve existing exact Activity navigation and pending-edit guards; saves refresh guarded workspace version. Source tables have no six-column recommendation cap. Read-only admin and submitted views cannot mutate. Reviewer can edit names/columns/membership, delete custom/source tables with fallback Other, confirm pending table interpretation.
- AI adds optional AiActivity.ref and optional activity_tables with ref/name/kind/source metadata/columns(ref,label,assay,metric,unit,activity_refs). Stable explicit refs map revision records, legacy activities preserve fallback pairing. Table edits carry AI audit, invalidate affected viewing/section confirmation and table status; unchanged human data preserved. Updated records and dependents require reviewer reconfirmation, not only unviewed state.
- Snapshot/publication/export/history support optional table collection and legacy hash compatibility. AI table edits excluded from reviewer-only approval diff, while later human table corrections remain visible. Current submitted/published snapshots immutable.

## Steps and ownership

1. Backend storage/service/API/migration/snapshot/review/history + tests. Use separate disposable PostgreSQL ending _test; DB suites serial. Test permission/version/ref integrity, Other complement, confirmation invalidation, snapshot compatibility, deletion dependencies and undo.
2. AI contracts/import/export/revision/approval projection + tests and guidance. Test legacy serialization, exact refs, scoped preservation, AI re-confirmation and exclusion from approval diffs. Update current guides and generated schemas without rewriting frozen bundles.
3. Frontend server-backed tables + Other, edit/save/confirm, local import and read-only access. Unit and browser tests include stable navigation/version handling and no scientific edits from browsing.
4. Full relevant verification and independent review. Preserve root uncommitted work and integrate only scoped changes. Deploy additive migration with fresh verified backups and service guards, retaining auth/Ketcher/CSP and production records.
5. Read current run handoffs and model configuration. Freeze two eligible paper identity/version baselines and scoped instructions; dispatch one fresh gpt-6-astra/high revision per paper using actual task adapter. Supervise through terminal/delivery, no automatic retry. Verify tables/Other coverage, pending re-confirmation, human preservation and reviewer-only approval projection. Record runtime metadata, receipts and final handoff.
