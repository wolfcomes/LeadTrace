# LeadTrace Backup Runbook

## Scope and policy

LeadTrace keeps two independently verifiable backup streams on a physically
separate disk or a controlled network destination:

- PostgreSQL: every four hours, and immediately before a schema migration or
  release publication.
- Assets: a daily incremental archive and a weekly full archive. The first
  incremental archive after a full archive is a full tar snapshot; retain the
  complete chain.
- Retention: 30 days, subject to the organization's legal hold policy.
- Restore drill: monthly, using a new database and a new asset directory.

The destination must be provisioned before scheduling. It must be an existing,
dedicated absolute directory, and `LEADTRACE_DESTINATION_ID` must identify the
disk or controlled network share. Never point a backup job at `/`, `$HOME`, `~`,
the source asset tree, or the application worktree.

Each finalized directory contains encrypted payloads and
`backup-metadata.json`. Metadata records the application, schema, and release
versions, UTC start/end times, outcome, artifact sizes and SHA-256 hashes,
encryption algorithm and key fingerprint, destination identity, and backup
scope. It never records database URLs, passwords, cookies, tokens, private
keys, or absolute source paths.

## Environment

Set these values in a root-readable environment file or a protected scheduler
unit. Do not put the file in the repository:

```text
LEADTRACE_BACKUP_DESTINATION=/srv/leadtrace-backups
LEADTRACE_BACKUP_ALLOWED_PARENT=/srv
LEADTRACE_DESTINATION_ID=leadtrace-backup-disk-a
LEADTRACE_DESTINATION_KIND=separate_disk
LEADTRACE_ENCRYPTION_RECIPIENT=age1...
LEADTRACE_ENCRYPTION_FINGERPRINT=SHA256:...
LEADTRACE_DATABASE_URL=postgresql+psycopg://...
LEADTRACE_ASSET_ROOT=/var/lib/leadtrace/assets
LEADTRACE_ASSET_ALLOWED_PARENT=/var/lib/leadtrace
LEADTRACE_APPLICATION_VERSION=0.1.0
LEADTRACE_SCHEMA_VERSION=0015_crop_job_subscriptions
LEADTRACE_RELEASE_VERSION=release-17
```

The age identity used for a restore is kept separately from the backup
destination and is readable only by the restore operator.

## Manual execution

Run from the repository checkout with the environment loaded:

```bash
bash leadtrace/ops/backup/backup_postgres.sh
LEADTRACE_ASSET_BACKUP_MODE=full bash leadtrace/ops/backup/backup_assets.sh
python leadtrace/ops/backup/verify_backup.py \
  /srv/leadtrace-backups/<backup-id>/backup-metadata.json
```

The scripts write to a staging directory, verify every output, and rename the
directory into place only after verification succeeds. A non-zero exit leaves
the previous finalized backups untouched. Investigate a failed job before
retrying; do not manually delete a staging directory outside the exact
destination shown in the error.

A full asset backup starts a new chain. Each successful asset backup atomically
updates `.leadtrace-latest-assets`; the daily incremental job verifies that
pointer and its complete parent chain automatically. An operator may set
`LEADTRACE_ASSET_PARENT_METADATA` to a specific finalized metadata file for a
controlled rehearsal, but the scheduled job does not require daily config
edits. Manifest and tar are generated from the same protected staging snapshot,
and source/destination ancestor overlap is rejected before staging begins.

## Scheduling

Use a service account with read access to PostgreSQL/assets and write access
only to the backup destination. Install the versioned units from
`leadtrace/ops/systemd`, review `WorkingDirectory`, `User`, and environment-file
paths for the host, then enable the timers:

```bash
sudo install -m 0644 leadtrace/ops/systemd/*.service /etc/systemd/system/
sudo install -m 0644 leadtrace/ops/systemd/*.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now \
  leadtrace-backup-postgres.timer \
  leadtrace-backup-assets-incremental.timer \
  leadtrace-backup-assets-full.timer \
  leadtrace-backup-retention.timer \
  leadtrace-restore-drill.timer
```

The timers implement the four-hour database, daily incremental, weekly full,
daily 30-day retention, and monthly restore-drill policy. Immediately before a
migration or release, run `leadtrace-backup-gate.service` and require a
successful exit plus verified metadata before continuing.

The scheduler must capture exit status and alert on any missing or failed
backup. Do not treat a file's presence as success; run `verify_backup.py` and
retain its output with the scheduler record.

## Verification and retention

At least once per day, list finalized directories and verify each metadata file.
At least once per week, verify a full asset archive and its manifest. Retention
cleanup must use an explicit list of dated child directories generated by the
backup service; never run a recursive deletion against the destination root.

Preview the exact verified direct children first, then apply the same command:

```bash
.venv/bin/python leadtrace/ops/backup/prune_backups.py \
  --destination /srv/leadtrace-backups --allowed-parent /srv \
  --retention-days 30
.venv/bin/python leadtrace/ops/backup/prune_backups.py \
  --destination /srv/leadtrace-backups --allowed-parent /srv \
  --retention-days 30 --apply
```

Record the latest successful database and asset backup IDs, their destination
identity, and verification timestamps in the operations log. Rotate age keys
under a documented key-rotation procedure; keep the old decryption identity
until every backup encrypted to it expires.
